# Repository Review Report

**Repository**: `C:\Users\lucia\git_projects\ai-platform-project-v1`

## Risks

- **[HIGH] corp-admin gate accepts forged JWTs (no signature verification)** — `_require_corp_admin` in apps/knowledge_platform/api/routes.py base64-decodes the JWT payload and reads `cognito:groups` without verifying the signature — the code comment states this outright ('Does NOT verify the JWT signature'). Any attacker who can reach the public API can hand-craft an unsigned token with `cognito:groups: ["corp-admins"]` and pass the check. This dependency guards every LinkedIn Review route: list, PATCH edit, POST regenerate, POST publish, DELETE reject. Impact is publishing arbitrary content to the owner's real LinkedIn account (LinkedInPublisherAgent pulls a live access token from Secrets Manager) and destroying drafts. Contrast with apps/corp_api, which is correctly protected by an API Gateway Cognito JWT authorizer that validates before Lambda invocation — the control exists in the codebase and was simply not applied here.
- **[HIGH] Unauthenticated ingestion allows RAG poisoning and unbounded LLM/embedding spend** — `POST /api/v1/kp/ingest-skill` (apps/knowledge_platform/api/routes.py) and `POST /api/v1/ingest` (apps/rag_demo/api/routes.py) declare no auth dependency — only a session Depends. Anyone reaching the public API Gateway can write arbitrary documents into pgvector under app_name 'skills_hub' or 'rag_demo'. Two consequences: (1) integrity — injected content is retrieved and summarised by AI Chat, and ReportIndexerAgent-adjacent content is trusted as grounding; (2) cost — each call triggers embedding generation. The MAX_EMBEDDING_CALLS_PER_RUN / MAX_CHUNKS_PER_DOC caps in settings.py are per-request/per-run limits and do not bound the number of requests, so the AWS Budget alerts at 10/25 CHF are the only backstop and they are detective, not preventive.
- **[HIGH] Arbitrary local file read via attacker-controlled source_uri** — `IngestRequest.source_uri` is passed unvalidated from the unauthenticated `POST /api/v1/ingest` into `get_loader(request.source_uri)` and then `loader.load()`, which calls `Path(source).read_text()`. There is no allowlist, no path-traversal check, and no scheme restriction in ingest_service.py or loaders.py. SUPPORTED_EXTENSIONS deliberately includes .py, .yaml, .toml, .sql, .tf, .json, and .md via CodeFileLoader. The Dockerfile COPYs aiplatform/ and apps/ into /app, so a request for /app/aiplatform/settings.py would ingest the source into the vector store, after which its contents are retrievable through the equally unauthenticated /api/v1/kp/query. This is a file-read-to-disclosure chain composed entirely of intended features.
- **[HIGH] Unauthenticated cross-namespace query defeats app_name isolation** — `POST /api/v1/kp/query` constructs `QueryService(session, app_name=None)` — the comment says 'search across all indexed content' — and has no auth dependency. The app_name column is the platform's primary logical data-separation mechanism (documented in CLAUDE.md and enforced in VectorStore.search), and this endpoint deliberately bypasses it for anonymous callers. Everything in ai-platform-db-v2 (skills_hub, rag_demo, knowledge_platform reports, plus anything an attacker ingested via the gap above) is returned with source_uri and excerpt. The corporate DB is a physically separate instance and is not exposed by this route.
- **[MEDIUM] LLM API keys and DB connection string stored as plaintext Lambda environment variables** — deploy_lambda.py, deploy_radar_pipeline.py, deploy_competitor_pipeline.py, deploy_regulatory_pipeline.py, and deploy_token_price_pipeline.py all call `settings.openai_api_key.get_secret_value()` and inject OPENAI_API_KEY, ANTHROPIC_API_KEY, and the full DATABASE_URL (credentials inline) into `Environment.Variables`. Any principal with lambda:GetFunctionConfiguration — a common read-only grant — retrieves them in cleartext. The pattern is inconsistent within the repo: deploy_corp_api.py grants a scoped secretsmanager:GetSecretValue policy for CORP_DATABASE_URL, and deploy_content_pipeline.py attaches a Secrets Manager policy for LinkedIn tokens. The safer pattern is already implemented and understood; it was not applied to the pipeline and RAG functions.
- **[MEDIUM] AUTH_BYPASS environment flag grants unconditional admin on the corporate API** — apps/corp_api/auth/cognito.py returns `UserClaims(user_id='dev-user-local', email='dev@local', groups=['admin'])` whenever the env var AUTH_BYPASS == 'true', before raising 401. This is a legitimate local-dev affordance, but it is a single string in Lambda configuration away from disabling Cognito auth and require_admin RBAC on the one stack that holds private corporate documents and audit logs. deploy_corp_api.py does not currently set it, and there is no guard preventing it from taking effect when APP_ENV == 'production' — settings.py already exposes `is_production`, which would make such a guard trivial.
- **[MEDIUM] Stored XSS in generated report HTML via unvalidated URL schemes** — The `_esc()` helpers in reporter.py, competitor_reporter.py, and regulatory_reporter.py escape &, <, >, and " — sufficient for text nodes but not for href attribute values. competitor_reporter.py emits `<a href="{_esc(s['url'])}" ...>` where the URL originates from scraped competitor sources, Hacker News hits, or LLM output; regulatory_reporter.py does the same for source URLs. A `javascript:alert(1)` payload contains none of the escaped characters and survives intact. These reports are uploaded to S3 under stable keys (competitor/reports/latest.html) explicitly intended for portfolio embedding, so execution context is a browser the owner or a visitor controls.
- **[MEDIUM] Indirect prompt injection from scraped and community-sourced content** — analyzer.py, competitor_analyzer.py, and regulatory_analyzer.py interpolate untrusted text directly into LLM prompts: article content from RSS/HTML scrapes, Hacker News titles fetched via the Algolia API in _fetch_hn, and regulatory document diffs. ContentCreatorAgent then consumes the resulting signal summaries to draft LinkedIn posts. An attacker who controls a monitored source or simply posts to HN can attempt to steer classifications (Adopt/Trial/Assess/Hold), impact/sentiment ratings, or the text of a draft post. Truncation to ~800 chars and the strict JSON output schema with allowlist validation (_VALID_CATEGORIES, _VALID_SIGNAL_TYPES) meaningfully constrain the blast radius — the free-text fields (signal_text, summary, title) remain the practical injection surface. Mandatory human review before LinkedIn publication is the compensating control.
- **[LOW] Untrusted XML/HTML/PDF parsing without hardening** — collector.py and competitor_collector.py parse remote feeds with `xml.etree.ElementTree.fromstring` on attacker-influenceable content; regulatory_collector.py parses remote PDFs with pypdf and HTML with lxml. stdlib ElementTree is not hardened against entity-expansion / billion-laughs style payloads, and there is no response size cap before parsing. Realistic impact is denial of service or Lambda timeout on a single scheduled pipeline run rather than data exposure, and the pipelines already catch per-source exceptions and continue.
- **[LOW] Infrastructure identifiers committed to a public-facing repository** — infra/vpc_config.json commits the AWS account ID (759302162548), VPC ID, all four subnet IDs, both security group IDs, the NAT Gateway Elastic IP (18.198.232.164), and the RDS endpoint hostname; infra/sns_config.json commits the SNS topic ARN. These are not credentials and the RDS instance has no public endpoint, but for a repository presented as a public portfolio they reduce reconnaissance cost for targeted attacks against a known account.
- **[LOW] Default database credentials committed in configuration** — The pair aiplatform:aiplatform appears in docker-compose.yml, alembic.ini's sqlalchemy.url, the settings.py default for database_url/alembic_database_url, and the _CORP_DATABASE_URL fallback in corp_db.py. These are local-development defaults and are overridden from the environment in deployed contexts (env.py sets the URL from settings; deploy scripts inject the real DATABASE_URL). The residual risk is a deployment that silently falls back to a default rather than failing closed, and the normalisation of weak credentials.
- **[LOW] Dependencies declared with lower-bound constraints only** — pyproject.toml pins every runtime dependency with >= rather than == or a compatible-release range — including openai, anthropic, boto3, sqlalchemy, and the document parsers (pypdf, lxml, beautifulsoup4, pdfplumber, openpyxl) that process untrusted external input. uv.lock exists and `uv sync --frozen --no-dev` in the Dockerfile means builds are reproducible in practice, which substantially mitigates this; the risk is that a lock refresh can silently pull an unvetted version of a parser sitting directly on the untrusted-input path.

## Assumptions

- I assumed the public API Gateway (72w6p1rx38.execute-api.eu-central-1.amazonaws.com) exposes /api/v1/ingest, /api/v1/query, and /api/v1/kp/* to the internet with no authorizer and no WAF. deploy_lambda.py creates the HTTP API with a Target integration and CORS but configures no authorizer — in contrast to deploy_corp_api.py, which explicitly creates a 'cognito-jwt' JWT authorizer and sets AuthorizationType per route. The severity of the four highest-rated risks depends entirely on this assumption.
- I assumed the credentials read by the deploy scripts via settings (OPENAI_API_KEY, ANTHROPIC_API_KEY, DATABASE_URL) are live production credentials rather than throwaway demo keys.
- I assumed the Lambda container filesystem at runtime matches the Dockerfile, which COPYs aiplatform/ and apps/ into /app — making supported-extension source files reachable by an absolute-path source_uri.
- I assumed report HTML written to S3 (including the stable competitor/reports/latest.html key) is rendered in a browser somewhere — the README describes latest.html as intended for portfolio embedding, which is what makes a javascript: href executable rather than inert.
- I assumed AUTH_BYPASS is never set in any deployed Lambda environment. deploy_corp_api.py's build_env_vars() does not set it, so this holds for a clean deploy from this repo.
- I assumed Cognito user pool IDs and app client IDs embedded in the frontend (platform-auth.ts, deploy_corp_api.py) are non-secret public SPA identifiers, which is correct for a client with GenerateSecret=False.
- I assumed the content indexed under app_name 'skills_hub' and 'rag_demo' is genuinely public/non-sensitive as CLAUDE.md states, which is why I rated the unauthenticated cross-namespace query on integrity and namespace-bypass grounds rather than as a confidentiality breach.
- I assumed the /compliance documentation reflects intended controls rather than verified-in-production state — compliance_mapping_v2.md itself flags 'No WAF on Corp API Gateway' as an open medium-risk gap.

## Open Questions

- Is there an API Gateway authorizer, WAF, resource policy, or network restriction in front of the public API that is provisioned outside this repository? If so, the ingest, query, and LinkedIn risks drop substantially; if not, they are directly exploitable by anyone with the URL.
- Are the LinkedIn Review routes reachable from the internet? If yes, the signature-less JWT check in _require_corp_admin is the only barrier between an anonymous caller and the owner's LinkedIn account — this is the single question that most changes the assessment.
- Has AUTH_BYPASS ever been set on a deployed Lambda, and is there any deploy path outside deploy_corp_api.py (console edit, CI, manual update-function-configuration) that could set it?
- What is the actual sensitivity of documents ingested under 'skills_hub' and 'rag_demo'? The Private Knowledge Hub explicitly scopes personal documents to app_name='private_hub' and is described as local-only — has any private_hub-scoped data ever been written to the shared ai-platform-db-v2 that the app_name=None query would now surface?
- Are the S3 report objects public-read, served via CloudFront, or embedded in an iframe on bridging-data.com? This determines whether the URL-scheme XSS has a real execution context.
- Was the account ID / VPC / RDS endpoint disclosure in infra/*.json a deliberate choice for a portfolio project, or should those files be gitignored and regenerated locally?
- Is there any rate limiting or usage plan on the public API Gateway beyond the per-run in-process caps in settings.py? Without one, the unauthenticated ingest endpoint is a direct cost-abuse vector against the OpenAI key.
- Which pipelines, if any, are permitted to run against attacker-controlled sources you do not own? The HN Algolia search in _fetch_hn is the clearest case where a third party can place text into your LLM prompt context at will.
